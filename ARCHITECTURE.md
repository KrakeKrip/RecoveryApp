# Архитектура RecoveryApp

## Текущее состояние

Проект — Swift Package для macOS 14+ и arm64. Большая часть логики и GUI сейчас
находятся в одном executable target `RecoveryApp`.

PhotoRec, `mmls`, `fls`, `icat` и `untrunc` запускаются отдельными процессами.
Sleuth Kit нельзя напрямую линковать с GPL-кодом приложения без отдельной
юридической оценки.

## Целевая CLI-first структура

```text
RecoveryCore
├── модели и пользовательские ошибки
├── обнаружение внешних дисков
├── проверка источника и назначения
├── запуск и отмена дочерних процессов
├── mmls/fls/icat, PhotoRec и untrunc
└── события прогресса

RecoveryCLI
└── команды и JSON/JSONL над RecoveryCore

RecoveryApp
└── SwiftUI над RecoveryCore
```

GUI и CLI не должны содержать две реализации recovery-логики.

## Контракт CLI

- Исполняемый файл: `recoveryapp-cli`.
- Человекочитаемый вывод — русский, автоматизация — `--json`.
- Длительные операции позже используют JSON Lines.
- Диагностика идёт в stderr, машинный результат — в stdout.
- Ненулевой код означает документированную ошибку.
- CLI не принимает пароль текстом.

## Read-only поток

```text
повторное обнаружение диска
→ Authorization Services
→ authopen только для чтения
→ проверка режима и размера native helper-ом
→ унаследованный файловый дескриптор
→ отдельный PhotoRec или Sleuth Kit CLI
→ результат на другом физическом диске
```

## Физический быстрый режим в RecoveryCore

Общий backend лежит в `RecoveryCore` (`PhysicalQuickRecovery.swift`) и
используется и GUI, и CLI без второй копии алгоритма:

- `PhysicalDriveSelector` принимает уже полученный снимок `[ExternalDrive]`
  и сверяет `diskN` (только формат `disk` + цифры), точное имя и точный размер
  до Authorization Services; вызов `diskutil` и авторизация остаются снаружи;
- папка результата проходит публичный preflight (существует, каталог, запись,
  не в точках монтирования источника) до Authorization Services; `recover`
  повторяет те же проверки вторым барьером;
- `PhysicalQuickRecovery` создаёт авторизационную сессию лениво и держит её на
  экземпляре: scan и все `icat` одной команды переиспользуют одну внешнюю
  форму прав — один системный запрос;
- запуск `recoveryapp-metadata-helper` отдельным процессом; helper независимо
  проверяет `O_RDONLY`, фактический размер устройства и запрет результата на
  источнике, переносит дескриптор на stdin и передаёт `/dev/fd/0`;
- коды helper 77/74/73/130 переводятся в типизированные ошибки;
- отмена завершает группу процессов tool-launcher.

## Глубокий PhotoRec в RecoveryCore

Общий backend лежит в `RecoveryCore` (`PhotoRecDeepRecovery.swift`) и
используется GUI (`DeletedFilesExecutor` — тонкий адаптер) и CLI без второй
копии алгоритма:

- backend владеет запуском PhotoRec и read-only helper, созданием уникальной
  папки сессии внутри выбранной папки результата, поиском результатов
  (`Recovered.*`), снимками прогресса и отменой;
- процессы запускаются с рабочей папкой сессии, поэтому `photorec.ses`,
  журнал и marker-файлы не появляются в каталоге, из которого вызвали CLI;
- образный режим: PhotoRec читает обычный файл-образ по сигнатурам JPEG, PNG
  и MOV/MP4; физический режим: тот же `recoveryapp-readonly-helper`
  (`O_RDONLY`, проверка размера, запрет результата на источнике, остановка
  дочерней группы по marker-файлу), одна авторизационная сессия передаётся
  снаружи после сверки источника и preflight папки;
- отмена: для физического источника ставится `.recoveryapp-stop`, helper сам
  останавливает группу PhotoRec; для образа сигнал по группе лончера; папка
  сессии и найденные файлы при отмене не удаляются;
- снимки прогресса (`PhotoRecProgressSnapshot`) считаются из `photorec.ses`,
  `.recoveryapp-progress`, журнала и подсчёта найденных файлов; значения,
  которые нельзя достоверно определить, остаются `nil` (не нулём); ETA не
  вычисляется.

### CLI-контракт deep recover

```text
recoveryapp-cli deep recover --image ФАЙЛ --output ПАПКА [--jsonl]
recoveryapp-cli deep recover --drive diskN --expected-name ИМЯ
    --expected-size БАЙТЫ --output ПАПКА [--jsonl]
```

- предварительный скан не нужен: команда сразу запускает PhotoRec;
- для физического источника повторное обнаружение, сверка id/имени/размера и
  preflight папки выполняются до Authorization Services; raw-путь `/dev/rdiskN`
  не принимается; пароль CLI не принимает ни в каком виде;
- коды выхода: 0 — успех (включая пустой результат), 1 — ошибка выполнения,
  2 — неверные аргументы, 130 — остановка по Ctrl-C;
- в режиме `--jsonl` stdout содержит по одному валидному JSON-объекту на
  строку: `started` (версия схемы, источник, папка сессии), `progress`
  (прошедшее время, найдено файлов, доступные счётчики чтения/объёма — ключ
  опускается, если значения нет), `completed` (папка сессии, число и пути
  файлов), `cancelled` (папка сессии и уже найденные файлы), `error`
  (стабильный код и понятное сообщение). Диагностика — в stderr;
- текстовый режим на русском: запуск и диагностика в stderr, итог и папка
  сессии в stdout, живой прогресс без ETA.

## Исправление видео в RecoveryCore

Общий untrunc-бэкенд лежит в `RecoveryCore` (`VideoRepair.swift`) и
используется GUI (`VideoRepairView` → `VideoRepairExecutor`) и CLI без второй
копии алгоритма:

- preflight до запуска: оба входа существуют, являются обычными читаемыми
  файлами и не совпадают даже через symlink или жёсткую ссылку (сверка
  разрешённого пути и пары «том + инод»); папка результата существует,
  доступна для записи, не является файлом;
- политика носителя: идентичность фактического тома (`st_dev` по
  разрешённому пути) сравнивается для исходников и папки результата с учётом
  symlink; результат на томе исходного видео запрещён, а неопределимый том —
  безопасный отказ (`volumeIdentityUnknown`). Поставщик метаданных
  внедряется только в доменных тестах; производственные CLI и GUI всегда
  используют системную реализацию;
- имя результата (`_recovered`, `_recovered_2`, …) резервируется атомарно
  (`O_CREAT | O_EXCL`), поэтому повторный и параллельный запуски не
  перезаписывают существующие файлы; при ошибке и отмене удаляется только
  недописанный файл текущей операции, чужие файлы не трогаются;
- запрос отмены запоминается и не теряется до запуска процесса (та же схема,
  что в PhotoRec-бэкенде); Ctrl-C останавливает всю группу
  `tool-launcher`/`untrunc`;
- исходные видео открываются только на чтение и не изменяются.

### CLI-контракт video repair

```text
recoveryapp-cli video repair --reference ФАЙЛ --damaged ФАЙЛ --output ПАПКА [--jsonl]
```

- `--json` для этой команды не поддерживается; `--drive`, `--image`, `--all`
  и незаявленные параметры дают код 2;
- в режиме `--jsonl` stdout содержит по одному валидному JSON-объекту на
  строку: `started` (`event`, `schemaVersion`, абсолютные `reference`,
  `damaged`, `outputDirectory` — после успешного preflight, до запуска
  инструмента, поэтому потоково), `completed` (абсолютный `result`),
  `cancelled` (`result` только при достоверно готовом файле), `error`
  (стабильный `code` и понятное `message`); диагностика и сырой вывод
  untrunc — только в stderr;
- коды выхода: 0 — успех, 1 — ошибка исполнения или preflight, 2 — ошибка
  аргументов, 130 — отмена; после ошибки/отмены живых дочерних процессов нет;
- текстовый режим краткий и русский, с путём результата и прошедшим временем;
  проценты, скорость и ETA не показываются.

## Размерная сверка quick-результатов

- Ожидаемый размер берётся из колонки размера `fls -l`: образный скан
  добавляет `-l` к `fls`, физический helper добавляет `-l` к своему запуску
  `fls` (больше в helper ничего не менялось). Короткий формат вывода означает
  неизвестный размер. Ноль в этой колонке означает, что TSK не заполнил
  метаданные записи, а истинный ноль по нему отличить нельзя, поэтому он
  консервативно трактуется как неизвестный размер (`expectedSize == nil`),
  а не как достоверно пустой файл.
- Каждый опубликованный файл получает статус: `expectedEmpty` (зарезервирован
  для достоверно известного нулевого источника и нулевого результата),
  `sizeMatches`, `incomplete` (короткий файл сохраняется в папке результата),
  `sizeMismatch`, `sizeUnknown` (неизвестный ожидаемый или фактический
  размер). Код 0 от `icat` полноту не гарантирует — сверка размеров выявляет
  неполные результаты; при ошибке чтения атрибутов `actualSize` остаётся
  неизвестным, а не нулём: значение `nil` в модели, а синтезированный
  Encodable целиком опускает JSON-ключ `actualSize` (выводится не `null`).
- `recover() -> [URL]` сохранён для GUI как тонкая обёртка над
  `recoverDetailed()`, возвращающей URL, ожидаемый и фактический размер и
  статус по каждому файлу.
- Пустой результат скана — нормальный исход: CLI завершается кодом 0 с
  понятным текстом либо с пустым отчётом (`recoveredCount: 0`, пустые
  `files`/`items`, нулевые счётчики); проверки папки результата и источника
  выполняются и в этом случае.
- JSON восстановления содержит прежние `recoveredCount`/`files` плюс
  `items` (построчные статусы) и `statusCounts` (агрегаты); текстовый режим
  предупреждает о неполных и несовпадающих размерах.
- Совпадение размеров не является побайтной проверкой целостности
  содержимого: метаданные файловой системы могут быть неполными.

## Физическая приёмка и её границы

Исправление Sleuth Kit на прямой `dup()` — и в чтении сегментов
(`tsk/img/raw.c`), и в определении размера
(`tsk/util/file_system_utils.c`) — пересобрано и проверено синтетически
(TASK-002). Физический CLI-путь (TASK-004) коротко проверен на Flashka
22 сентября 2026 года: `authopen` запросил разрешение один раз, `mmls`
нашёл раздел, `fls` начал читать exFAT через `/dev/fd/0` без прежнего отказа
`Permission denied`. Полный проход 125-ГБ накопителя и извлечение файлов в
этом тесте не выполнялись; их результат остаётся неподтверждённым.
