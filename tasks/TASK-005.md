# TASK-005 — CLI PhotoRec: глубокое восстановление, прогресс и отмена

## Статус и ветка

- Статус: `IN PROGRESS`.
- Задание подготовлено координатором в `main`. Ветка должна начинаться от
  текущего `main` после коммита задания; полный базовый хеш будет передан GLM
  вместе с коротким стартовым сообщением.
- Ветка: `glm/task-005-cli-photorec`.

## Цель

Добавить CLI для глубокого восстановления PhotoRec из образа и физического
накопителя. Реализация PhotoRec должна жить в `RecoveryCore`; GUI и CLI должны
вызывать один backend. CLI показывает фактический прогресс и корректно
останавливает весь процесс PhotoRec по Ctrl-C, сохраняя уже найденные файлы.

## Текущая реализация, которую нужно сохранить

- Глубокий PhotoRec сейчас реализован в
  `Sources/RecoveryApp/DeletedFilesRecovery.swift`; не создавай вторую
  независимую копию алгоритма для CLI.
- Для физического диска используется
  `Packaging/recoveryapp-readonly-helper.c`: он открывает источник только для
  чтения, проверяет размер и запрет результата на исходном устройстве,
  запускает PhotoRec отдельным процессом, пишет `.recoveryapp-progress` и
  останавливает дочернюю группу по marker-файлу. Не ослабляй эти проверки.
- Для образа PhotoRec получает текущий набор сигнатур JPEG, PNG, MOV/MP4 и
  сканирует образ целиком. Сохрани текущие параметры PhotoRec и совместимость
  существующего GUI-сценария.
- Прогресс GUI уже получает из `photorec.ses`, `.recoveryapp-progress`, журнала
  и подсчёта найденных файлов. Перенеси повторно используемые расчёты в Core.
- PhotoRec может создавать `photorec.ses` в текущей рабочей папке процесса.
  Новая реализация должна запускать процесс с рабочей папкой сессии, чтобы не
  оставлять этот файл в каталоге, из которого пользователь вызвал CLI.

## Объём

1. Создай PhotoRec backend в `Sources/RecoveryCore/` для обоих источников:
   - регулярный файл-образ;
   - выбранный физический диск (`ExternalDrive`).
   Backend владеет запуском PhotoRec/helper, созданием уникальной папки сессии,
   поиском результатов, снимками прогресса и отменой. Тип результата сессии
   должен быть доступен и GUI, и CLI. В `DeletedFilesRecovery.swift` оставь
   тонкий GUI-адаптер, который делегирует Core и сохраняет существующие
   пользовательские callbacks/поведение.
2. Добавь команды:

   ```text
   recoveryapp-cli deep recover --image IMAGE --output DIR [--jsonl]
   recoveryapp-cli deep recover --drive diskN --expected-name NAME --expected-size BYTES --output DIR [--jsonl]
   ```

   Глубокий режим сразу запускает PhotoRec; отдельный предварительный `scan` не
   нужен. Для физического источника обязательны ID, точное ожидаемое имя и размер.
   Не принимай raw-путь `/dev/rdiskN` вместо повторного обнаружения диска.
3. Папка `DIR` должна существовать, быть доступной для записи и пройти текущие
   проверки назначения. Для физического источника повторно обнаружи диск,
   сверяй ID/имя/размер и проверь расположение результата до Authorization
   Services. Используй текущий `authopen`/read-only helper и одну сессию
   авторизации. CLI никогда не принимает пароль аргументом или из stdin.
4. Создавай уникальную папку текущей сессии внутри выбранного `DIR`; результаты
   PhotoRec должны находиться только внутри неё. Не удаляй папку при отмене:
   файлы, уже найденные PhotoRec, должны остаться доступными. `photorec.ses`,
   журналы и временные данные не должны появляться за пределами папки сессии.
5. Добавь текстовый режим на русском и машинный режим `--jsonl`. В JSONL stdout
   содержит только по одному валидному JSON-объекту на строку; сообщения и
   техническая диагностика идут в stderr. Зафиксируй в документации и тестах
   минимальный контракт событий:
   - `started`: версия схемы, источник и папка сессии;
   - `progress`: прошедшее время, число найденных файлов и доступные фактические
     счётчики чтения/объёма результата;
   - `completed`: папка сессии, число и пути сохранённых файлов;
   - `cancelled`: папка сессии и уже найденные файлы;
   - `error`: стабильный код ошибки и понятное сообщение.

   Значения, которые пока нельзя достоверно определить, опускай или кодируй
   согласно принятому JSON-контракту; не подменяй их нулём. Не показывай ETA.
   Скорость сообщай только при наличии реальных измерений.
6. Ctrl-C должен запросить отмену в общем backend, дождаться остановки всей
   группы PhotoRec/helper и завершиться кодом `130`. В JSONL выдай итоговое
   событие `cancelled`; уже найденные файлы и каталог сессии сохраняются.
   Успех завершается кодом `0`, ошибка выполнения — `1`, ошибка аргументов — `2`.
7. Обнови справку CLI, `ARCHITECTURE.md`, `STATUS.md` и README только в части
   нового PhotoRec CLI-контракта. В `TASKS.md` оставь TASK-005 в `REVIEW` при
   сдаче; статус `DONE` устанавливает координатор после проверки.

## Критерии приёмки

- GUI и CLI используют одну PhotoRec-реализацию в RecoveryCore; в GUI target не
  остаётся копии алгоритма запуска/отмены PhotoRec.
- Текстовый CLI сообщает запуск, живой прогресс по доступным реальным метрикам,
  число найденных файлов и папку сессии. Точного ETA нет.
- `--jsonl` выдаёт только валидные события в stdout и сохраняет потоковый вывод
  при длительной операции; отдельная проверка разбирает каждую строку JSON.
- Обычный успех, пустой результат, ошибка инструмента и Ctrl-C имеют
  документированные коды и понятные сообщения. После Ctrl-C нет живых
  PhotoRec/helper дочерних процессов; найденные до отмены файлы остаются.
- В image-режиме PhotoRec работает с образом; в drive-режиме сохраняются
  повторное обнаружение/сверка, read-only helper, проверка размера и запрет
  назначения на исходном диске.
- Вызов CLI из постороннего рабочего каталога не оставляет там `photorec.ses`,
  логи, marker-файлы или результаты.
- Видимый интерфейс и раскладка SwiftUI не меняются; GUI deep-recovery делегирует
  новый backend. Не меняй иконку, версию/build, поиск Sleuth Kit, untrunc,
  сеть, телеметрию или автообновление.
