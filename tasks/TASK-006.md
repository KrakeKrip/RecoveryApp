# TASK-006 — общий backend и CLI исправления видео

## Статус и ветка

- Статус: `IN PROGRESS`. Только Codex переводит задачу в `DONE` после ревью.
- Ветка GLM: `glm/task-006-cli-video-repair`, от точного коммита `main`,
  который координатор передаст в коротком стартовом сообщении.
- Работать только по этому заданию. TASK-007 и TASK-008 не начинать.

## Цель

Сделать исправление повреждённого видео доступным из CLI для быстрых
автоматических проверок без запуска окна приложения. Вынести существующий
`untrunc`-алгоритм из `Sources/RecoveryApp/VideoRepair.swift` в общий
`RecoveryCore`: GUI и CLI используют один backend, а нынешний SwiftUI-сценарий
продолжает работать без изменения видимого интерфейса.

## Что уже есть и что сохранить

- GUI принимает исправный пример, повреждённый файл и выбранную папку; вызывает
  `untrunc -n -dst ...` через `tool-launcher`, показывает очищенный лог, умеет
  остановить группу процессов и открыть готовый файл в Finder.
- Имена результата имеют суффиксы `_recovered`, `_recovered_2` и далее без
  перезаписи существующих файлов. Сохрани этот пользовательский принцип.
- Есть переменные `RECOVERYAPP_UNTRUNC_PATH` и
  `RECOVERYAPP_TOOL_LAUNCHER_PATH` для тестов; сборка `.app` содержит оба
  инструмента. Не добавляй зависимости, не пересобирай сторонние библиотеки.
- `Scripts/test-video-repair.sh` проверяет реальный встроенный `untrunc` на
  синтетическом H.264/AAC MP4; `Tests/Fixtures/slow-untrunc.sh` и
  `Scripts/test-cancellation.sh` показывают модель проверки дочернего PID.

## Объём работ

1. Перенеси модели запроса и ошибок, preflight, выбор имени результата, запуск,
   чтение/очистку лога и отмену группы `untrunc` в `Sources/RecoveryCore/`.
   Сохрани совместимость GUI-адаптера `VideoRepairExecutor`, его callback и
   пользовательских карточек результата/ошибок. В GUI target не должно быть
   второй реализации запуска или отмены `untrunc`.
2. Добавь команду:

   ```text
   recoveryapp-cli video repair --reference ФАЙЛ --damaged ФАЙЛ --output ПАПКА [--jsonl]
   ```

   Пути могут быть относительными на входе, но в машинном выводе они
   абсолютные. `--json` для этой команды не поддерживается. Не принимай
   пароль, `--drive`, устройство `/dev/...` или незаявленные параметры.
   Отсутствующая подкоманда/значение, дубли и конфликтующие флаги дают код 2.
3. До запуска проверь, что оба входа существуют, являются обычными читаемыми
   файлами и не указывают на один и тот же файл даже через symlink; папка
   результата существует, доступна для записи и не совпадает с входным
   файлом. Не записывай результат на физический накопитель с исходным видео:
   проверяй идентичность фактического тома/носителя с учётом symlink и
   отказывай безопасно, когда её нельзя надёжно определить. Для проверки
   этой политики используй синтетические тома или внедряемый источник
   метаданных, но не подключённые пользовательские флешки. Не ухудшай уже
   существующие проверки источника и назначения других режимов.
4. Исходные файлы должны оставаться неизменными. Итоговое имя не должно
   перезаписывать существующий файл даже при повторном/параллельном запуске.
   При ошибке и отмене не показывай недописанный файл как успешный результат;
   уборка допускается только для временного файла именно текущей операции.
   Чужие файлы и ранее созданные результаты не удаляй.
5. `--jsonl`: stdout содержит только по одному валидному JSON-объекту на
   строку; диагностика и сырой вывод `untrunc` идут только в stderr. Запиши
   и протестируй минимальную схему версии 1:
   - `started`: `event`, `schemaVersion`, абсолютные `reference`, `damaged`
     и `outputDirectory` (после успешного preflight, до запуска инструмента);
   - `completed`: `event`, `schemaVersion`, абсолютный `result`;
   - `cancelled`: `event`, `schemaVersion`; путь указывать только если есть
     достоверно готовый файл;
   - `error`: `event`, `schemaVersion`, стабильный `code`, понятный `message`.

   Текстовый режим — краткий русский вывод с путём результата. Можно
   сообщать прошедшее время, но нельзя выдумывать процент, скорость или ETA.
   Событие `started` должно поступать потоком, не только при завершении.
6. Ctrl-C запрашивает отмену общего backend, дожидается остановки всей группы
   `tool-launcher`/`untrunc` и возвращает код 130. Коды: 0 — успех, 1 — ошибка
   исполнения или preflight, 2 — ошибка аргументов, 130 — отмена. После
   ошибки/отмены не должно оставаться дочерних процессов. Понятные сообщения
   нужны для отсутствующего/нечитаемого входа, недоступной папки, результата
   на исходном носителе, нехватки места, повреждённого/отсутствующего
   инструмента и отсутствующего готового файла; технические коды — в stderr.
7. Обнови справку CLI, `ARCHITECTURE.md`, `README.md` и `STATUS.md` только в
   части этой команды и её реально проверенного поведения. Версию/build,
   иконку, PhotoRec, Sleuth Kit, сеть, телеметрию и автообновление не меняй.
   Если обнаружится необходимость более широкого решения, остановись и
   сообщи координатору, а не расширяй задачу молча.

## Критерии приёмки и проверки

- Добавь `Scripts/test-video-cli.sh` с безопасной уникальной временной папкой:
  аргументы/коды 2, preflight/коды 1, JSONL по строкам, stdout без лога,
  потоковый `started`, повтор без перезаписи, входы с неизменными SHA-256,

  shim с дочерним процессом: Ctrl-C, код 130 и отсутствие живых PID. Проверь
  недоступный инструмент и имитацию нехватки места. Не использовать личные
  видео и физические накопители.
- Добавь доменные проверки для одинакового файла через symlink, не-файла на
  входе, недоступной папки/носителя и конкурентного выбора имени. Если для
  тома нужен тестовый seam, он не должен позволять отключать защиту в
  производственном CLI/GUI.
- Выполни `./Scripts/test.sh`, `./Scripts/test-cli.sh`,
  `./Scripts/test-video-repair.sh`, `./Scripts/test-cancellation.sh`, новый
  `./Scripts/test-video-cli.sh`, `./Scripts/test-deep-photorec-cli.sh`,
  `./Scripts/test-quick-image-cli.sh`, `./Scripts/test-deleted-recovery.sh`.
  Не выдавай синтетический тест за проверку пользовательского накопителя.
- Собери release CLI и `.app` в отдельную временную папку (не перезаписывай

  укажи в отчёте.

  сделай его безопасным для повторного запуска.
