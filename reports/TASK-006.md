# REPORT TASK-006

## Коммит

Полный хеш итогового коммита сообщается Codex в ответе исполнителя: отчёт входит
в сам итоговый коммит, поэтому хеш коммита невозможно записать внутри него.
Ветка: `glm/task-006-cli-video-repair`, базовый коммит
`72efed0014d673672d528a49112de0b49c95ef0c` (совпадает с `main` на момент старта).

## Реализовано

- Untrunc-алгоритм исправления видео перенесён в общий `RecoveryCore`
  (`Sources/RecoveryCore/VideoRepair.swift`); из GUI target реализация
  удалена (`Sources/RecoveryApp/VideoRepair.swift` удалён). В Core живут
  модели запроса и ошибок, preflight, политика носителя, атомарный выбор
  имени результата, запуск через `tool-launcher`, потоковая очистка лога
  (`LogSanitizer`) и отмена группы процессов. `VideoRepairExecutor` сохранён
  как публичный тип с прежним API (`run(request:onOutput:)`, `cancel()`), к
  нему добавлен необязательный `onValidated` — GUI-сценарий и его callbacks
  не изменились, в GUI target нет второй реализации запуска/отмены.
- Preflight усилен (общий для GUI и CLI):
  - оба входа — существующие обычные читаемые файлы; совпадение входов
    отклоняется по разрешённому пути и по фактической паре «том + инод»,
    то есть включая symlink и жёсткие ссылки (`sameInputFiles`);
  - папка результата существует, доступна для записи, не является файлом
    (`outputFolderIsFile`);
  - политика носителя: фактический том (`st_dev` по разрешённому пути)
    папки результата сравнивается с томами обоих исходников; результат на
    томе исходного видео запрещён (`resultOnSourceVolume`), а неопределимый
    том даёт безопасный отказ (`volumeIdentityUnknown`). Поставщик
    `VideoVolumeDeviceProvider` внедряется ТОЛЬКО в доменных тестах
    (harness); производственные CLI и GUI всегда используют системную
    реализацию `systemVolumeDevice` — отключить защиту через seam нельзя;
  - существующие проверки других режимов (quick/deep) не менялись.
- Имя результата: прежний принцип `_recovered`, `_recovered_2`, … сохранён;
  имя резервируется атомарно `O_CREAT | O_EXCL` (`reserveResultURL`), поэтому
  повторный и параллельный запуски получают разные имена и никогда не
  перезаписывают существующие файлы (поведение untrunc с уже существующим
  пустым файлом назначения проверено — он заполняет плейсхолдер). При ошибке
  и отмене удаляется только недописанный файл текущей операции (плейсхолдер
  известен backend'у); чужие файлы и ранее созданные результаты не
  затрагиваются и не публикуются как результат. Исходные видео открываются
  только на чтение; их SHA-256 проверены тестом до и после.
- Отмена: запрос запоминается и не теряется до запуска процесса (проверка
  под той же блокировкой, что и регистрация Process, плюс перечитывание флага
  сразу после `run()` — та же схема, что принята в PhotoRec-бэкенде после
  ревью TASK-005); Ctrl-C останавливает всю группу `tool-launcher`/`untrunc`.
- CLI: новая команда
  `recoveryapp-cli video repair --reference ФАЙЛ --damaged ФАЙЛ --output ПАПКА [--jsonl]`
  - пути принимаются относительными, в машинном выводе абсолютные;
  - `--json` для команды запрещён (код 2); `--drive`, `--image`,
    `--expected-*`, `--all`, дубли, отсутствующие значения и незаявленные
    параметры дают код 2; пароль не принимается; `/dev/...` на входе
    отклоняется валидацией как не-обычный файл (`inputNotRegularFile`);
  - события JSONL (schemaVersion 1): `started` (абсолютные `reference`,
    `damaged`, `outputDirectory` — после успешного preflight и
    резервирования, ДО запуска инструмента, т.е. потоково), `completed`
    (абсолютный `result`), `cancelled` (`result` только при достоверно
    готовом файле — когда untrunc успел завершиться и Core проверил файл;
    ключ опускается для недописанного), `error` (стабильный `code` +
    понятное `message`); stdout не содержит лога untrunc — диагностика и
    сырой вывод инструмента только в stderr;
  - коды выхода: 0 — успех, 1 — ошибка исполнения или preflight, 2 —
    ошибка аргументов, 130 — отмена; после ошибки/отмены живых дочерних
    процессов нет;
  - текстовый режим краткий и русский: «Видео восстановлено за м:сс. Файл
    результата: …»; проценты, скорость и ETA не показываются;
  - понятные сообщения для отсутствующего/нечитаемого входа, каталога
    вместо входа, совпадающих входов, недоступной папки, файла вместо
    папки, результата на исходном носителе, неопределимого тома, нехватки
    места, отсутствующего инструмента и отсутствующего готового файла;
    технические коды — в stderr.
- Справка CLI, `ARCHITECTURE.md` (раздел «Исправление видео в
  RecoveryCore» + CLI-контракт), `README.md` (раздел «CLI исправления
  видео»), `STATUS.md` обновлены только в части новой команды; `TASKS.md` —
  статус TASK-006 `IN PROGRESS` → `REVIEW`. Версия/build, иконка, PhotoRec,
  Sleuth Kit, сеть, телеметрия и автообновление не менялись.
- `Scripts/test-video-repair.sh` стал безопасным для повторного запуска:
  фикстура создаётся в уникальном подкаталоге `run-$RANDOM-$$` внутри
  `VIDEO_FIXTURE_DIR`, сам корень больше никогда не удаляется — указание
  пользовательской папки через переменную теперь не может её стереть.

## Риски и отклонения от задания

- Отклонений от объёма задания нет; ограниченные решения зафиксированы:
  1) новые случаи `VideoRepairError` получили отображения в
  `UserFacingFailure` (GUI), 2) плейсхолдер результата резервируется до
  запуска untrunc (поведение untrunc с существующим файлом назначения
  проверено вручную — он заполняет его), 3) при ошибке/отмене удаляется
  только файл текущей операции.
- Разбор `st_dev` опирается на `stat()` по разрешённому пути; если том
  определить нельзя (например, недоступная ФС), операция отказывает
  (`volumeIdentityUnknown`), а не пишет «куда-нибудь» — это требование
  задания; ложные отказы возможны только на нестандартных ФС без `stat`.
- Политика «другой том» означает: CLI/GUI-исправление видео с входами и
  выходом на одном диске теперь отклоняется; это соответствует требованию
  задания, но сужает прежнее поведение (раньше такой сценарий проходил).
- JSONL-контракт рассчитан только на добавление новых ключей; переименование
  существующих полей нарушило бы контракт автоматизаций.
