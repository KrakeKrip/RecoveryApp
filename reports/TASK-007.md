# REPORT TASK-007

## Коммит

Полный хеш итогового коммита сообщается Codex в ответе исполнителя: отчёт входит
в сам итоговый коммит, поэтому хеш коммита невозможно записать внутри него.
Ветка: `glm/task-007-swiftui-core-parity`, базовый коммит
`ec4ad7f67b15849022f2392971f4fcb3e0a48757` (совпадает с `main` на момент старта).

## Исправление по замечанию ревью (второй коммит ветки)

- **Устаревание находок при обновлении списка накопителей.** `scan` теперь
  фиксирует идентичность подтверждённого источника
  (`scannedSourceIdentity`, `diskN`+имя+размер); `refreshDrives()` после
  обновления списка проверяет её через `ScannedSourceRefresh.outdatedReason`:
  если диск с тем же `diskN` изменил имя или размер — находки, выбор и
  физическая quick-сессия сбрасываются и показывается карточка «Источник
  изменился» (`sourceChanged`); если источник исчез — карточка «Накопитель
  отключён» (`sourceUnavailable`). Всё до авторизации; во время операции
  проверка пропускается (операция сверяет источник сама, а уже открытый
  read-only дескриптор принадлежит проверенному устройству).
- **Тестируемость.** `DeletedFilesViewModel` принимает внедряемый провайдер
  снимка накопителей (`driveSnapshot`) и экземпляр `DeletedFilesExecutor`;
  production использует значения по умолчанию (реальные
  `ExternalDriveDiscovery`/Core), seam не управляется переменными окружения
  и не позволяет обходить политику. ViewModel выделен в отдельный файл
  `DeletedFilesViewModel.swift` без SwiftUI (Combine + Foundation), чтобы
  доменный harness мог собирать его вместе с Core.
- **Тесты** (+10 доменных проверок, 215 → 225): сценарий «скан → обновление →
  тот же disk7, другое имя и размер» — находки и выбор очищены,
  `scannedSourceIdentity == nil`, карточка `sourceChanged`, quick-сессия
  пересоздана (счётчик фабрики); обновление без изменений идентичности
  оставляет находки; исчезновение источника даёт `sourceUnavailable`.
  Контрольный запуск пересобранной `.app` на синтетическом FAT32-образе:
  скан → восстановление → зелёная карточка «Восстановление завершено»
  («Сохранено файлов: 1»), форматирование и подпись без изменений.

## Исправление по второму замечанию ревью (новый коммит ветки)

- **Очистка устаревших находок в любом состоянии экрана.** Прежняя проверка
  в `refreshDrives()` срабатывала только в состоянии `.scanFinished`: после
  ошибки выбора папки (`.failed`) подменённый диск с тем же `diskN` при
  обновлении списка оставлял старые `candidates`/`selection`. Теперь сброс
  находок, выбора, идентичности скана и quick-сессии выполняется при любом
  состоянии экрана (кроме активной операции — там источник сверяет сама
  операция, а открытый read-only дескриптор принадлежит проверенному
  устройству), с карточкой «Источник изменился» (`sourceChanged`) или
  «Накопитель отключён» (`sourceUnavailable`).
- **Дополнительная сверка в `recoverSelected`.** После
  `confirmPhysicalSource` подтверждённый диск сверяется с сохранённой
  идентичностью источника сканирования (`scannedSourceIdentity`); при
  несовпадении операция отказывает (`sourceChanged`) ДО preflight,
  авторизации и запуска инструмента, а чужие находки и идентичность
  очищаются. Это закрывает случай «список уже показывает B, а находки
  остались от A» (например, обновление прошло во время операции и было
  пропущено).
- **Идентичность скана сохраняется после ошибки/отмены** (`handle()` больше
  не сбрасывает её): находки остаются для повторной попытки на том же
  носителе, но обновление списка при подмене носителя всё равно отбросит их
  в любом состоянии.
- **Тесты** (+12 доменных проверок, 225 → 237): полная цепочка ревью
  «скан A → ошибка выбора папки на A → подмена на B с тем же diskN →
  обновление → выбор допустимой папки → восстановление недоступно
  (`canRecover == false`)»; защита `recoverSelected` — при подтверждённом B
  и идентичности скана A операция отказывает (`sourceChanged`), чужие
  находки и идентичность очищены, сессия пересоздана.

## Реализовано

- **Единая сверка источника через Core.** Ручная копия сверки
  `diskN`/имени/размера удалена из всех трёх действий `DeletedFilesViewModel`
  (scan, recoverSelected, deepRecover). Введён общий помощник
  `confirmPhysicalSource`: заново получает снимок через
  `ExternalDriveDiscovery` и сверяет выбранный диск через
  `PhysicalDriveSelector.selectDrive` (правила — только в Core). При
  исчезновении/подмене диска операция отказывает (`sourceUnavailable`/
  `sourceChanged`) до авторизации, показывается прежняя карточка ошибки,
  физическая quick-сессия сбрасывается.
- **Preflight до авторизации.** Для физического `recoverSelected` preflight
  папки результата (`PhysicalQuickRecovery.preflightRecoveryOutput`)
  выполняется сразу после сверки, до создания новой авторизации и запуска
  инструмента; для физического `deepRecover` общий preflight перенесён в
  начало `deepRecover(drive:)` адаптера, до `ReadOnlyAuthorization`. Core и
  helper сохраняют свои повторные проверки как вторые барьеры. Выбор папки
  во время операции по-прежнему заблокирован; запрет папки на источнике
  работает и через symlink (preflight Core сверяет точки монтирования по
  разрешённым путям — покрыто доменным тестом).
- **Одна физическая quick-сессия.** Новый
  `PhysicalQuickSessionCoordinator` держит пару «идентичность источника
  (`diskN`+имя+размер) → `PhysicalQuickRecovery`»: scan и recoverSelected
  подтверждённого источника переиспользуют один экземпляр и его ленивую
  авторизационную сессию; другой `diskN` получает новую сессию; смена
  источника, отмена (`cancel()` останавливает группу процессов активной
  сессии и сбрасывает её), ошибка и завершение извлечения сбрасывают сессию
  безопасно. Подменная фабрика `makeRecovery` — узкий seam только для
  доменных тестов; production GUI всегда строит реальный backend Core
  (`makePhysicalRecovery`), обхода политики через переменную окружения нет.
  `authopen`, helper, `O_RDONLY`, проверка размера и запрет записи на
  источник не менялись.
- **Детальные quick-результаты в GUI.** Образное и физическое извлечение
  переведены с `recover() -> [URL]` на `recoverDetailed()` Core:
  `DeletedFilesExecutor.recoverDetailed` возвращает `[RecoveredFileResult]`.
  Новый `QuickRecoverySummary` агрегирует статусы для карточки: число
  сохранённых файлов не уменьшается из-за статуса; при
  `incomplete`/`sizeMismatch` карточка получает спокойный оранжевый тон и
  заголовок «Восстановление завершено с предупреждениями» с точными
  счётчиками; `sizeUnknown` объясняется отдельно и не выдаётся за
  доказанную полноту; каждый итог напоминает «Совпадение размеров не
  является проверкой целостности содержимого»; проблемные файлы не
  удаляются, кнопка «Открыть папку» работает как раньше; пустой результат
  (results.isEmpty) — нормальное состояние `scanFinished` с текстом
  «восстанавливать нечего», без ложной ошибки и без успеха «сохранено 0».
- **Остальные направления на общем Core.** GUI deep делегирует
  `PhotoRecDeepRecovery` (preflight физического режима — общий метод Core),
  видео — `VideoRepairExecutor` из Core. Алгоритмы процессов, parsing,
  прогресса и выбора имени результата в SwiftUI не переносились;
  UI-форматирование (счётчики, заголовки) осталось в ViewModel.
- **Сохранено без изменений:** карточки успеха/отмены/ошибки (кроме
  задуманного статуса-заголовка quick-карточки), Finder-кнопки, выбор
  диска/образа/папки, русский текст, прогресс без ETA, режим без
  автоматического сна, подробный лог, иконка, версия/build 0.8.1 (13),
  CLI-контракты, сеть/телеметрия/обновления, упаковка, source-only права.
