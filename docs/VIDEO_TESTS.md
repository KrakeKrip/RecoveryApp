# Проверки восстановления видео

Дата: 2026-09-12

## Зафиксированная сборка

- `anthwlock/untrunc` commit `9d86ec9ef2ffed1bf8131abe80742c0574db52b6`
- FFmpeg 8.1, минимальная статическая конфигурация из Makefile проекта
- arm64 Mach-O, 13 МБ
- нет ссылок на `/opt/homebrew`; только `libSystem`, `libiconv` и `libc++` macOS

## Успешный сценарий

Созданы два синтетических MP4 640×360, 30 fps, H.264 + AAC, 5 секунд. Из тестовой
копии удалён финальный атом `moov`. Встроенный `untrunc` восстановил файл за менее
чем секунду. `ffprobe` подтвердил два потока и длительность 5,034667 секунды.
SHA-256 исправного примера и повреждённого входа до и после операции совпали.

Тот же сценарий полностью пройден через собранное приложение: выбор трёх путей,
запуск, отображение результата и подробного лога. Полученный GUI-файл также прошёл
проверку `ffprobe`.

## Ошибка

Через GUI выбран один и тот же файл как пример и повреждённое видео. Запуск
заблокирован доменной проверкой с сообщением: «Исправный пример и повреждённое
видео должны быть разными файлами».

## Отмена

`tool-launcher` создаёт отдельную POSIX-группу процессов. Автоматический тест
запустил контролируемое дерево из лидера и дочернего процесса, отправил SIGTERM
группе и подтвердил отсутствие обоих PID.

GUI-тест с медленным контролируемым инструментом показал прошедшее время,
«Оставшееся время неизвестно» и кнопку «Остановить». После нажатия приложение
осталось открытым, показало «Операция остановлена», дочерний PID исчез.

## Что эти тесты не доказывают

- Не проверены HEVC, ProRes, экшн-камеры, смартфоны, большие файлы и реальные сбои
  записи.
- Отмена реального длительного `untrunc` ещё не проверена на многогигабайтном
  синтетическом файле; механизм группы процессов проверен контролируемым деревом.
- Качество восстановленных кадров оценивалось только структурно через `ffprobe`,
  без покадрового сравнения.
